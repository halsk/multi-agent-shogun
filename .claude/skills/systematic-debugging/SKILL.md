# systematic-debugging

## 目的

Iron Law #2 **「原因なき修正禁止」** を実行可能な手順として具体化する。
**真因（root cause）特定後** に修正する。「とりあえず動かす」「workaround で済ます」「try-catch で握り潰す」は禁止。

## 適用範囲

- バグ修正タスク全般
- 「動かない」「期待と違う」「障害が出た」の調査
- パフォーマンス問題の原因特定
- インフラ / デプロイ失敗の解析

## 手順

### Step 1: 症状の正確な記述

調査開始前に、以下を **書き出す**：

- **どこで**: ファイル・関数・行・サービス名
- **何が起きているか**: エラーメッセージ全文・期待と実際の差
- **再現手順**: 最小再現コマンド・入力・環境
- **いつから**: git log / git bisect の手がかり、デプロイ履歴
- **影響範囲**: 1 ユーザのみ / 全体 / 特定環境のみ

### Step 2: 仮説立案（複数）

可能性のある原因を **複数** リスト化。**1 つに飛びつかない**。

```
仮説 A: <原因候補>
  予測: もしこれが真なら <こういう挙動> を観測するはず
  検証手段: <ログ確認 / テスト実行 / curl 等>

仮説 B: <別の原因候補>
  予測: ...
  検証手段: ...

仮説 C: ...
```

確からしさ順に並べる。最低 3 つは出すよう努める（1 つしか思いつかない時こそ盲点が潜む）。

### Step 3: 仮説検証

各仮説を **客観的に検証可能な手段** で確認：

- ログ / プリント出力 / debugger
- 真偽が分かれる入力で挙動を比較
- ユニットテストで仮説を表現 (修正前に **失敗する** テストが書けたら強い証拠)

**反証された仮説は捨てる**。「多分これだろう」のまま修正しない。

### Step 4: 真因確定

1 つの仮説に絞れる証拠が揃った時点で真因確定。
- 「想定通り」と「現実」の **完全一致** を確認
- 真因が **既知の不変条件 (invariant) を破っている** ことを言語化できるはず

例:
- ❌ 「null チェックを足したら直った」（症状緩和、真因不明）
- ✅ 「<関数> は <前提条件> を仮定しているが、<入力源> はそれを満たさない場合があった」（真因明確）

### Step 5: 修正設計

真因に基づく修正方針を立てる：
- 副作用の有無を検討
- 同じ真因が他箇所で発生していないか grep
- テストケースを **先に** 書く（テストファースト）

### Step 6: 修正実装 + 検証

- 修正前: 失敗するテストが書けている
- 修正後: 当該テストが PASS、他のテストが regress していない
- [verification-before-completion](../verification-before-completion/SKILL.md) skill に従って完了報告

## アンチパターン（禁止）

| アンチパターン | なぜ駄目か |
|--------------|----------|
| try-catch で握り潰し | 真因隠蔽、別の場所で爆発 |
| if 分岐で症状回避 | 真因放置、デッドコード化 |
| `--no-verify` で hook bypass | 安全装置の無効化、根本未解決 |
| 「動いたから OK」 | 偶然動いた可能性、再発リスク |
| Stack Overflow コピペ | 自分のケースに合うか未検証 |
| 「環境のせい」で打ち切り | 環境差が真因なら、それを言語化して再現可能にすべし |
| 量で押し切る （複数 fix を bulk commit） | どの変更が効いたか不明、再発時辿れない |

## エスカレーション

以下の場合は **即座に殿/家老に報告して判断を仰ぐ**：

- 3 仮説いずれも検証で反証された（盲点の可能性）
- 真因が「上流 OSS の bug」「インフラ設定」「権限」等、修正範囲外
- 修正に大規模 refactor が必要
- 1 時間以上の調査でも真因が絞れない
